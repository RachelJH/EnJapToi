# Paper와 함께 시작·종료하는 수신기

## 변경 이유와 동작

이전 수신기는 Paper와 별도로 실행되고 Python SQLite에 먼저 저장했습니다. 서버가 꺼져 있는 동안 받은 후원이 다음 실행에서 게임 효과로 이어질 수 있었습니다.

현재는 플러그인이 Python을 자식 프로세스로 생성하고 stdin 쓰기 파이프를 소유합니다. 정상 disable 시 파이프를 닫고 자식 종료를 기다립니다. JVM이 강제 종료돼도 OS가 쓰기 핸들을 닫습니다. Python의 전용 감시 스레드는 EOF/파이프 오류를 감지하면 네트워크 작업이나 다른 스레드의 종료를 기다리지 않고 프로세스 전체를 끝냅니다. 시간 기반 heartbeat의 유예 시간 동안 계속 수집하는 구조가 아닙니다. OAuth 잠금도 OS 잠금으로 바꿔 강제 종료 후 잠금 파일이 남아도 다음 실행을 막지 않도록 했습니다.

실시간 receiver.py는 Paper 관리 파이프와 실행 식별자가 없으면 인증 전에 종료합니다. OAuth 최초 로그인과 오프라인 donation_check.py, 기존 bridge.py 관리용 모의 전송은 계속 독립 실행할 수 있습니다.

## 접수와 보존의 경계

- 서버 실행 중 수신한 유효 후원만 기존 게임 규칙으로 변환합니다. 금액 확인이 없으면 기존 관찰/전달 차단을 유지합니다.
- 자동 모드에서는 후원을 Python 디스크에 저장하지 않고 Paper에 바로 접수합니다. 응답 불명확 시 같은 ID·효과로 현재 실행 중 즉시 한 번 재시도합니다.
- Paper가 queued/duplicate로 접수한 항목의 영속성은 기존 events.sqlite3가 담당합니다. Yirue가 오프라인이어도, 서버를 다시 켜도 PENDING과 중복 ID 기록은 보존됩니다. RUNNING/UNCERTAIN 처리도 유지합니다.
- 전송 중 서버가 종료되면 Paper가 이미 저장했을 수도 있습니다. 저장된 항목은 보존되고, 저장되지 않은 항목은 이후 실행용으로 따로 쌓지 않습니다. 이 경계에서 손실 없는 전달/정확히 한 번 실행을 보장하지 않습니다.
- 새 서버 실행마다 다른 식별자를 사용합니다. 자동 수신기가 보내는 X-EJT-Instance가 다르면 새 서버는 거부하므로 오래된 수신기가 재시작한 서버에 보내지 못합니다. 관리용 bridge.py 모의 테스트의 무표식 요청은 기존처럼 지원합니다.
- 이전 Python donations.sqlite3는 자동 이관·재생하지 않습니다. Paper가 이미 접수한 대기열은 삭제하지 않습니다.

## 테스트와 한계

실제 계정 없이 Python 테스트는 부모 파이프 EOF, 막힌 작업 중 전체 프로세스 종료, 서버 미응답 후원 미저장, 같은 ID 재시도, OS 잠금 강제 종료 복구를 검증합니다. Java 테스트는 정상 close, 종료 훅 없는 부모 JVM halt 후 Python 감시 동작, 이전 서버 식별자 거부, 기존 SQLite 강제 종료 복구를 검증합니다.

실제 Paper 230 테스트에서는 가짜 CHZZK 소스와 실제 Paper HTTP/DB를 사용합니다. 이 테스트가 실제 계정/Socket.IO 후원 수신 검증을 의미하지는 않습니다. Windows의 프로세스·DPAPI 실동작은 Windows PC에서 추가 확인이 필요합니다.

공식 DONATION 메시지에는 고유 ID와 발생 시각이 명시돼 있지 않습니다. 우리 수신기는 서버 종료 중 새 메시지를 수집하거나 과거 후원을 요청하지 않지만, 제공자가 다음 연결 후 늦게 전달한 메시지의 원래 발생 시각을 자동 판별할 수는 없습니다. 연결이 없던 동안의 후원을 복구한다는 보장도 하지 않습니다.

초기 설정은 README receiver 블록을 기존 config.yml에 추가하세요. Python 경로·스크립트·채널·매핑·클라이언트 파일은 절대 경로를 권장합니다. 비밀값은 config.yml이나 프로세스 인자에 넣지 않습니다. 설정이 안 된 기본값에서는 자동 수신을 비활성화하며, OAuth 오류 시 자동 재로그인하지 않습니다. 경로/인증 수정 후 Paper를 다시 시작합니다.
